# DOUBLE-READ EXHAUSTIVE AUDIT PROTOCOL V1.7.0

## PURPOSE
A review is complete only after the script has been read in full through all mandatory passes **and a final full saturation sweep finds ZERO new actionable defects**.

There is **NO MAXIMUM ISSUE COUNT**.
If 7 places need repair, list 7. If 47 places need repair, list 47. If 100+ places need repair, list all actionable places.
Never stop because the ledger feels long.

## READ 1 — WHOLE-STORY COMPREHENSION PASS
Read from first line to last line without publishing judgments mid-read.
Before Read 1, freeze the MASTER BASELINE character counts. Then build/refresh the silent maps:
- canon;
- timeline;
- knowledge state;
- object state;
- location/access;
- cause → effect;
- open loops;
- incentives;
- institution/professional behavior;
- prose/motif patterns.

Purpose: understand what the script is trying to do before criticizing how it does it.

## READ 2 — LINE-BY-LINE FORENSIC PASS
Read the entire script again from first line to last line.
This pass is adversarial and granular.
For every scene/paragraph/important line, test:
- does it contradict anything before/after?
- can the character know this yet?
- is the action physically possible?
- is time/distance/money/procedure plausible?
- does the clue follow from competence/evidence rather than luck?
- does a historical object/mechanism age realistically?
- does the legal/professional consequence require missing verification?
- is any object/location/state silently changing?
- is a line repetitive, overly neat, explanatory, generic, or AI-patterned?
- is a punchline/motif repeated too often?
- is there any sentence/paragraph that weakens retention or naturalness enough to warrant editing?

Every actionable finding goes into the candidate ledger immediately with a location marker.


## READ 3 — REVERSE DEPENDENCY PASS
Read from the ending backward by scene/Part (Part 7 → Part 1). Do not judge prose flow; trace dependencies:
- every payoff back to setup;
- every character knowledge claim back to acquisition;
- every object/location state back to transition;
- every age/date/season/money state backward;
- every legal/professional consequence back to authority/evidence;
- every ending condition back to a causal path.

This pass exists specifically to catch defects forward reading tends to normalize.

## COVERAGE MATRIX — NO BLANK CELLS
For each Part, explicitly mark PASS/PATCH internally for: timeline, money, knowledge, location/access, object state, clue setup/payoff, exact numbers, causality, law/authority, physical mechanics, professional realism, human incentives, retention, prose/TTS, spelling, platform, ending dependency and length. Any unclassified cell = audit incomplete.

## ZERO-NEW-DEFECT SATURATION PASS — FREEZE GATE
After all reads and sweeps, perform another full-script sweep.
- If any new actionable defect is found, add it to the ledger, update dependencies and score deductions, then repeat this saturation pass.
- Freeze only after one complete saturation pass returns **0 new actionable defects**.
- The visible first QA must therefore represent the saturated defect universe, not a sample of likely issues.

## OCCURRENCE ENUMERATION LOCK
Do not hide many edit locations behind one vague note.
If one root pattern appears in multiple places:
- create one root Patch Family if useful;
- enumerate **EVERY occurrence that needs editing** as O01, O02, O03...;
- each occurrence must have a recognizable location and a specific repair direction.

Example:
F07 — Excessive `Not X. Not Y. Z.` construction
- O01: Part 1, after discovery of key — merge into flowing sentence.
- O02: Part 3, confrontation — keep only the strongest contrast.
- O03: Part 6, reveal — preserve because it functions as climax emphasis.
Only actionable occurrences are marked for change; protected intentional uses are explicitly exempted.

## THIRD CHECK — OMISSION SWEEP
After Read 2, do a shorter third sweep across:
- every exact number/date/age/price/distance/time;
- every clue setup and payoff;
- every document/legal claim;
- every major decision;
- every repeated phrase/pattern;
- every patch location already captured plus its dependencies.

Ask:
“What would I be embarrassed to discover only after the rewrite?”
Add it now. Then run a repair-simulation sweep: for each candidate patch, inspect dependencies and expected length impact before freezing the ledger.

## COMPLETENESS OVER BREVITY
Visible explanations may remain concise, but omission is forbidden.
If the ledger is very long:
- shorten wording per issue;
- use compact tables/structured entries;
- group by Part/category;
- NEVER omit an actionable issue merely to keep the answer short.

## ACTIONABLE VS SUBJECTIVE
List every issue that should actually be changed to make the script more:
- logical;
- plausible;
- continuous;
- sharp;
- engaging;
- emotionally credible;
- professionally credible;
- human-written in feel.

Do not list a purely subjective alternate wording when the existing line is already strong and natural.
The threshold is not “major only”; the threshold is **would a careful human editor actually change this?**
If yes, include it, even if tiny.


## PUBLICATION SWEEP AFTER READ #2
Before freezing the ledger, run one final publication sweep for:
- Hook/title promise;
- Part-level rewrite necessity;
- MUST PRESERVE strong spans;
- character consistency;
- spelling/grammar/American-English usage;
- mature U.S. 40+ voice;
- YouTube suitability and avoidable advertiser-risk wording.


## ONE-SHOT SATURATION RULE
Do not publish the first review while any patch location, dependency, whole-Part rewrite decision, or length consequence is still vague. The ledger must be executable without rediscovering the script during rewrite.

These are part of completeness, not optional later discoveries.

Before publishing QA, silently certify:

`LAST SATURATION PASS NEW DEFECTS = 0`
